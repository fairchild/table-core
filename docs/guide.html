Guide

How to connect the store to your server and your UI. It covers what your server should return, what the store gives back and how counts, failures and selection work.

Quick start

npm install @fairchild/table-core

The package needs only AbortController and DOMException, which every browser and Node.js provide. To type-check against it, include the DOM library or @types/node.

Below is a complete client. It is examples/client.js, which the docs test runs against a pretend server and the live demo is built on. Your server answers two URLs:

GET /api/items?sort=due&dir=ascending
              &offset=0&limit=50
→ { rows: Item[],
    total?: number | { atLeast: number },
    nextCursor?: string | null }

GET /api/items/count?sort=due&dir=ascending
→ 310   (a plain number)
// A complete client: a store for /api/items, the
// query string it sends, and the count it shows.
// test/docs.test.ts runs this file against server.js,
// and the live demo on the landing page is built on it.
import { ServerRowsStore } from '@fairchild/table-core';

/** The view as a query string. Send it as you like. */
export function query(view, offset, limit) {
  const params = new URLSearchParams();
  const sort = view.sort[0];
  if (sort) {
    params.set('sort', sort.columnId);
    params.set('dir', sort.direction);
  }
  if (offset !== undefined) {
    params.set('offset', String(offset));
    params.set('limit', String(limit));
  }
  return params.toString();
}

// fetch() resolves on a 500 too. Check `ok`, or an
// error body is taken for an answer.
async function json(res) {
  if (!res.ok) throw new Error(`HTTP ${res.status}`);
  return res.json();
}

export function createItemsStore({
  fetch = globalThis.fetch,
  pageSize = 50,
} = {}) {
  const options = {
    view: { sort: [] },
    pageSize,
    // Resolves with { rows, total?, nextCursor? }.
    fetchRows: ({ view, offset, limit, signal }) =>
      fetch(`/api/items?${query(view, offset, limit)}`, {
        signal,
      }).then(json),
    // Resolves with a number: the view's exact count.
    // Asked only while a page's total is { atLeast }.
    fetchCount: ({ view, signal }) =>
      fetch(`/api/items/count?${query(view)}`, {
        signal,
      }).then(json),
  };
  const store = new ServerRowsStore(options);

  // update() takes every option: change the view and
  // pass the rest as they were.
  function sortBy(columnId, direction = 'ascending') {
    options.view = { sort: [{ columnId, direction }] };
    store.update({ ...options });
  }

  // "Select all" goes to the server as the view and
  // its exceptions, so it reaches rows not loaded yet.
  // Resolves with the ids the server archived.
  async function archive(selection) {
    const body = selection.kind === 'ids'
      ? { view: options.view, ids: [...selection.ids] }
      : { view: options.view,
          except: [...selection.except] };
    const res = await fetch('/api/items/archive', {
      method: 'POST',
      headers: { 'content-type': 'application/json' },
      body: JSON.stringify(body),
    });
    const { archived } = await json(res);
    store.reload();
    return archived;
  }
  return { store, sortBy, archive };
}

/** "50 of 310 items", or "50 of 100+ items" for now. */
export function countText({ rows, total }) {
  const fmt = (n) => n.toLocaleString('en-US');
  const items = (n) => (n === 1 ? 'item' : 'items');
  const shown = fmt(rows.length);
  if (total === undefined) {
    return `${shown} ${items(rows.length)}`;
  }
  if (typeof total === 'number') {
    return `${shown} of ${fmt(total)} ${items(total)}`;
  }
  return `${shown} of ${fmt(total.atLeast)}+ items`;
}

Then render the snapshot whenever it changes, start the store when the table appears and stop it when the table goes away. Load more is a button: loadMore() asks for the next page only once the current one has arrived, so calling it straight after start() does nothing.

import { createItemsStore, countText }
  from './client.js';

const { store, sortBy } = createItemsStore();
store.subscribe(() => {
  const snapshot = store.getSnapshot();
  // snapshot: { rows, state, total, paging }
  render(snapshot, countText(snapshot));
});
store.start(); // fetches the first page
moreButton.onclick = () => store.loadMore();
titleHeader.onclick = () => sortBy('title');
// When the table goes away: aborts what is in
// flight, keeps the cache.
store.stop();

The snapshot is plain data: { rows, state, total, paging }. It is a new object only when something changed, so comparing snapshots by identity is enough to skip work.

Everything else is a command:

  • store.update(config) when the view, page size or mode changes, with all the options (an option left out goes back to its default, except now);
  • store.loadMore() and store.setPage(n) to move;
  • store.retry() after a failure;
  • store.reload() after you change data on the server.

Your server's contract

Your fetchRows receives a request and returns a page.

Request fields
Request fieldMeaning
viewThe sort, and the filter if you set one. Plain data: send it to your server as you like.
offsetRows to skip. Always set, so offset-only servers work.
cursorIn load-more mode, the previous page's nextCursor. Prefer cursors (keyset paging) when rows move between requests.
limitThe page size.
signalAborted when the request is out of date or the store stops. Pass it to fetch.
Response fieldMeaning
rowsThe page's rows, in the view's order.
totalOptional. An exact number, or { atLeast: n } while the exact count is expensive. A number on every page keeps the count current with no separate count request.
nextCursorOptional. The next page's cursor, or null on the last page. Leave it out for offset paging.

The one rule for offset paging: without a cursor, a page with fewer rows than limit is the last page, unless its own total says there are more. Return limit rows whenever there are that many, or return cursors.

total is optional. With no total at all, a short page or a null cursor ends the list and counts the rows through it, and fetchCount is never called.

If your server reports { atLeast }, also give the store a fetchCount. It resolves with the count as a plain number: 310, not { count: 310 }. It is asked once per visit while the total is a lower bound, so a count that failed is asked again on the next visit. Until it answers, the total reads “50 of 1,000+”.

Load more or pages

mode: 'load-more' (the default) appends pages: page p is asked for only after page p − 1 arrives, with its cursor. snapshot.paging is { kind: 'load-more', hasMore }. loadMore() does nothing when there is no next page, so a double click can't fetch twice.

mode: 'pages' shows one page at a time and asks by offset only. snapshot.paging is { kind: 'pages', page, pageCount }, with page counted from 0. If rows are removed on the server and the page you are on no longer exists, the store moves to the last one that does. Without a count it finds that page by halving the distance, so a link to page 5,000 of a 100-page list takes about a dozen requests.

In load-more mode, the next page is asked for from the rows already loaded. If a short page wasn't the last (its total said there were more), no rows are skipped.

Reading the state

snapshot.state is a few independent facts rather than one status label, because a table can be, for example, showing good rows while the next page failed. The store always sets rows and fetching, so settled rows of the current view are { rows: 'current', fetching: false, since }.

FieldValuesMeaning
rows'current' · 'previous' · 'none'Whose rows are on screen: this view's, the last view's (kept while the new one loads, so the layout doesn't jump), or nothing yet.
fetchingbooleanRows are on the way.
sinceDateWhen the rows on screen were fetched.
failure{ message?, retry, scope }What failed. scope is 'load' (this view's rows), 'refresh' (rows already on screen) or 'more' (the next page).

One way to render them, as a starting point:

  • Skeleton rows: rows === 'none', fetching, no failure.
  • Busy (aria-busy): fetching while the rows on screen aren't this view's.
  • “Updating…” next to the count: fetching.
  • An alert for 'load' and 'more'. After a failed 'load', previous rows are hidden rather than passed off as the new view's.
  • A quiet notice, “Showing saved data from 10:42”, for 'refresh', with a Refresh button that calls failure.retry.

Views, caching and staleness

Pages are cached by pageKey(view, pageSize): the view and the page size both decide which rows a page holds. Coming back to a sort you saw a moment ago is instant.

A visit is one stay on a view and page. It starts on start(), on a new view, page size or mode, on setPage() and on reload(). A new visit:

  • aborts the last visit's page requests. A count for the same view carries on, except after reload(), which aborts it and asks again;
  • forgets the last visit's failures, so coming back to a view that failed asks the server again;
  • checks the cached pages it shows against staleAfter (30 s by default), once.

Stale pages are fetched again in the background while the old rows stay on screen. In load-more mode the whole chain is rebuilt aside and swapped in when complete, so you never see old and new pages mixed. If the list came back shorter, the rows past its new end are dropped.

Call reload() after you change data on the server: every cached page is marked stale, and what's on screen is fetched again in the same way.

Counts

The total in the snapshot is kept as consistent with the rows as the rows are with the server:

  • A number on a page sets the exact count. { atLeast } on a page sets a lower bound, and the store asks fetchCount, unless a short page at or past the bound, or a page with a null cursor, settles the count itself.
  • When rows are fetched again (staleness, reload()), a count that came from fetchCount is asked for again with them. One that came from a page is settled by the next page's total.
  • A refreshed lower bound above the old count replaces it at once. A count that answers after a newer page total doesn't overwrite it.
  • Until a new count arrives, the old one is still shown. It limits paging only for rows fetched before the recount began, so new rows on the server are reachable. In pages mode it stays a floor for the page count, so the pager doesn't shrink and grow back.
  • By offset, a short page ends the list and settles the count, unless its own total, or a count learned later, says there are more rows. An empty page always ends a load-more list. A count settled this way gives way when a later page brings more rows than it. In pages mode, an empty page that finds the count too high asks for a new count instead of guessing one.

Failures and retry

The store never retries by itself within a visit. Each failure says what it was about:

  • 'load': this view's rows (or this page's) failed. retry() asks again.
  • 'more': the next page failed; the rows on screen are fine. loadMore() or retry() asks again.
  • 'refresh': rows on screen couldn't be refreshed. They stay, with since, and so does the count that belongs to them. retry() starts a new visit and refreshes what is stale.

A fetcher that throws synchronously is treated like one that rejects. A fetcher that ignores its signal is harmless: a late answer to an aborted request is dropped.

Selection

A selection is one value, whichever way it was made:

type Selection =
  // these rows
  | { kind: 'ids'; ids: ReadonlySet<string> }
  // every row in the view, except these
  | { kind: 'all-matching'; except: ReadonlySet<string> };

The helpers are pure functions, so they work with any state library:

import {
  setSelected, isSelected, selectionCount,
  removeFromSelection, type Selection,
} from '@fairchild/table-core';

// Nothing selected:
let selection: Selection =
  { kind: 'ids', ids: new Set() };
selection = setSelected(selection, ['WI-1', 'WI-2'], true);
// "Select all 1,284":
selection = { kind: 'all-matching', except: new Set() };
// Untick one: it joins `except`.
selection = setSelected(selection, ['WI-7'], false);
const { rows, total } = store.getSnapshot();
selectionCount(selection, total, rows.length); // 1,283

// Rows deleted on the server leave the selection. They
// don't become exceptions: the server's new total no
// longer counts them.
await api.archive(['WI-9']);
selection = removeFromSelection(selection, ['WI-9']);
store.reload();

An all-matching selection counts against the view's total; while the total is a lower bound, so is the count.

To act on a selection, send it to your server as it is. “Select all” goes as the view and its exceptions, { view, except }, so the action reaches rows that were never loaded. The quick start's archive() does this. Clear the selection when the view's filter changes, so an action never reaches rows that aren't shown.

Using it from React

The store follows React's external-store contract, so a hook is a few lines:

function useServerRows(options) {
  const [store] = useState(
    () => new ServerRowsStore(options),
  );
  // Every render: the fetchers may change, and a new
  // view moves to its own cache entry.
  useLayoutEffect(() => { store.update(options); });
  useEffect(() => {
    store.start();
    return store.stop;
  }, [store]);
  const snapshot = useSyncExternalStore(
    store.subscribe, store.getSnapshot, store.getSnapshot,
  );
  const { loadMore, setPage, reload } = store;
  return { ...snapshot, loadMore, setPage, reload };
}

The commands are stable functions, so they're safe to pass to memoized rows. stop() keeps the cache, so a StrictMode remount doesn't refetch what it already has.

Testing your integration

Give the store a clock (now) and fetchers that return promises you settle yourself. The order of events is then exact, with no timers:

let clock = 0;
const pending = [];
const store = new ServerRowsStore({
  view: { sort: [] },
  pageSize: 2,
  staleAfter: 100,
  now: () => clock,
  fetchRows: (request) => new Promise(
    (resolve, reject) =>
      pending.push({ request, resolve, reject }),
  ),
});
store.start();
pending[0].resolve({
  rows: [{ id: 'a' }, { id: 'b' }],
  nextCursor: 'c1',
});
await new Promise((r) => setTimeout(r, 0));
store.getSnapshot().paging;
// { kind: 'load-more', hasMore: true }
clock += 101; // the page is now stale

What the tests cover

npm test runs node --test over test/, in the style above. Each file below drives the store one event at a time.

  • server-rows-store.test.ts: the cursor chain and reload, page size, cancellation, merged and late requests, StrictMode start/stop, the failure scopes, staleAfter and pages mode.
  • consistency.test.ts: rows, total and paging together through:
    • server growth and shrinkage between visits;
    • totals arriving before or after rows;
    • failed refreshes followed by retry;
    • servers that give exact totals on every page;
    • deep links and empty pages.
  • regressions.test.ts, server-shapes.test.ts and deep-links-and-rebuilds.test.ts: sequences that once broke, each failing before its fix, and the shapes real servers take: counts settled and redone across visits, failed rebuilds, deep links with no count and load-more offsets after a short page.
  • pages-refresh.test.ts: pages mode when a refresh fails or a count ages: saved rows stay, empty pages don't.
  • malformed-responses.test.ts and bad-totals.test.ts: answers that aren't rows, counts or totals fail like errors, in every position, and Load more stays offered while its page loads.
  • low-totals.test.ts: a total below the rows a page brings is read as a lower bound, so the list doesn't end on it.
  • filter.test.ts: a filter is part of a page's identity, and never shares the unfiltered view's cache entry.
  • selection.test.ts: the selection helpers, including deletions from both kinds of selection.
  • boundary.test.ts: no dependencies, and sources that import only each other.
  • docs.test.ts: these pages: every export documented, every link resolving, every code block within 60 columns, and the example client run against the example server.
